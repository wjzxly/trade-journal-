# 设计说明

## 为什么是这套结构

做这个项目之前，先想清楚一个问题：**什么样的交易记录系统真正有用？**

市面上的交易日记大多停在「记录」这一层——记下买卖价格、盈亏金额，然后画一条收益曲线。这类工具的问题在于，它只告诉你结果，不告诉你原因。收益曲线是涨的，你不知道是规则好还是运气好；是跌的，你不知道是规则错还是执行错。

要回答「原因」，最少需要三个维度的交叉：

1. **规则维度** —— 这笔交易属于哪条规则？（决定样本分组）
2. **执行维度** —— 我是否严格照规则做了？（分离规则问题和纪律问题）
3. **状态维度** —— 我当时是什么情绪？（挖掘行为模式）

三者缺少任何一个，归因就会塌陷成主观叙事。这就是四张表的由来。

## 表结构的设计意图

### rules —— 规则是假设，不是箴言

`condition` 字段存的不是自然语言，而是能被机器判定的表达式。这个约束是有意的：**写不成代码的规则，通常也执行不了**。

「要注意市场情绪」「要有耐心」这类说法听起来正确，但无法判定一次操作符不符合，因此也无法被验证。系统不允许这种规则存在。

`version` 字段承担一个重要职责：规则一旦改动就自动升版。原因很朴素——如果你边记录边改规则，前面的样本和后面的样本就不是同一件事了，混在一起统计等于自欺。升版后老样本仍归属旧版本，新样本归属新版本，各自统计。

### signals —— 把「看见」和「做到」分开

这是整个设计里最容易做错的地方。很多日记工具把「信号」和「交易」合并成一条记录，结果失去了最有价值的信息。

举个具体例子：某条规则触发了 40 次，你实际出手 25 次。这 15 次放弃本身就是重要样本：
- 如果放弃的那些事后都涨了 → 你错过机会，问题在犹豫
- 如果放弃的那些事后都跌了 → 你的直觉在补充规则，也许是规则该收紧了

`acted` 字段（NULL / 1 / 0）和 `skip_reason` 就是为了捕获这部分。

### trades —— followed 字段是整个系统的支点

```sql
followed  INTEGER NOT NULL DEFAULT 1
deviation TEXT    DEFAULT ''
```

只加这两个字段，就能把「规则行不行」和「我执不执行」彻底分开：

| | 赚钱 | 亏钱 |
| --- | --- | --- |
| **按规则** | 规则有效的证据 | 规则需要修改 |
| **偏离规则** | 危险：强化坏习惯 | 执行问题，规则无辜 |

没有 `followed`，所有亏损都会变成「这次运气不好」或者「大盘太差」，归因永远失真。

`deviation` 要求用第一人称写实话，因为「提前止盈了」这种中性描述掩盖了真实动机——真正该写的是「怕利润回吐，手抖卖了」。

### reviews —— 归因决定系统有没有用

`attribution` 的四个选项（rule / execution / market / luck）是对「甩锅」的防御设计。

统计归因分布本身就是一个诊断：如果一个人的复盘里 80% 是 `market`，说明他从来没真正检视过自己的规则。

## 规则引擎的设计

### 为什么不用 eval

最直接的实现是 `eval(condition, {}, row)`，五行代码搞定。但它同时引入了两个致命问题：

1. **注入**。个人工具里注入看起来危害不大，但规则是可以保存、导出、分享的，一旦扩散就是真实风险。
2. **语义失控**。`eval` 能跑 `__import__('os').system('rm -rf')`，意味着「规则」变成了任意代码，规则库不再是数据。

自己写一个递归下降解析器大约 200 行，换来的是：白名单字段、明确的错误信息、可缓存的 AST。这个代价是值得的。

### 为什么支持「字段 vs 字段」

第一版写成「左边字段，右边数值」，结果 `close > ma20` 直接报错——而这恰恰是最常用的写法。

这暴露了一个设计盲点：**约束应该加在语义上，而不是形式上**。现在两个操作数都可以是白名单字段，但都不允许是任意标识符，安全边界没有放宽。

### 为什么缺字段返回 False 而不是抛错

扫全市场时，缺数据是常态（停牌、新股、数据源滞后）。如果一缺字段就中断整批扫描，实用性会大打折扣。

缺失视为「条件不成立」是一个明确的取舍：宁可漏掉一个信号，不要中断整次扫描。

## 统计方法的选择

### Bootstrap 而不是 t 检验

样本量通常只有几十笔，收益率分布还明显不是正态的（有肥尾，有涨停限制）。这种情况下 t 检验的前提根本不成立，算出来的 p 值没有意义。

Bootstrap 重采样的好处是它不假设分布形状，而且**区间宽度本身就是信息**——样本少的时候区间会很宽，一眼就能看出「这还不能下结论」。

固定随机种子（42）是为了让同一份数据每次刷新结果一致，避免用户看到波动的区间产生困惑。

### R 倍数的近似

理想情况下 R 应该是 `盈亏 / 初始止损距离`，需要记录每笔的止损价。

第一版没有止损价字段，用固定 3% 折算。这是一个明确的近似，已知的偏差是：止损设得宽的规则，R 会被高估。

改进方向：`rules` 表加 `stop_loss_pct` 字段，配对时取对应规则的值。

### 离场规则的独立口径

一开始离场规则和入场规则用同一套判定，结果「破位离场」显示 0% 胜率、负期望值，结论是「这条规则该删」。

这显然是错的。止损规则的作用就是**亏得少**，它注定要亏。用「能不能赚钱」评价一个止损规则，就像用「能不能止血」评价一个手术刀。

现在按 `kind` 分流：`exit` / `risk` 类规则看最大单笔亏损是否被限制在阈值内，阈值 10 笔（而不是 30 笔，因为止损样本来得更快）。

## 前端为什么不引入框架

单页 HTML + 原生 JS，约 600 行。

理由：
- 个人工具，不需要路由、状态管理、组件复用
- 没有构建链意味着没有 `node_modules`、没有版本冲突、没有「先 npm install」
- 打开浏览器就能看，改一行刷新就生效

代价是 DOM 拼接字符串比较原始。如果将来功能扩展到多页、需要复杂交互，再迁移到框架也不迟——目前没有这个必要。

## 后续方向

按优先级：

1. **止损价字段** —— 修正 R 倍数近似，这是当前最大的统计精度问题
2. **行情接入** —— 用 akshare 或 tushare 拉日线，让「批量扫描」自动化
3. **规则组合分析** —— 现在只看单条规则，实际情况是两条规则叠加时的表现可能完全不同
4. **回测对照** —— 用历史数据跑规则，和真实操作对比，量化「执行损耗」
5. **导出报告** —— 生成季度复盘 PDF，用于自我审视
